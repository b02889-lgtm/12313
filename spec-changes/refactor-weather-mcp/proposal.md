# 提案：重构 Weather MCP Server (refactor-weather-mcp)

## 1. 动机 (Motivation)

当前 `weather-mcp-server` 是一个 286 行的单文件 MCP 天气查询服务。虽然功能可用，但在代码分析中发现了多个问题：

### 已确认的 Bug
- **URL 参数拼接不规范**：`units` 参数以裸值形式拼入 URL（`&m` 而非键值对），依赖 wttr.in 的非标准行为
- **城市名未做 URL 编码**：含空格或中文的城市名可能导致请求失败
- **hourly 数组硬编码索引**：假设数组长度 ≥ 17，API 返回不完整数据时会引发 `IndexError`

### 架构层面的技术债
- 所有逻辑集中在单个 `server.py` 文件中，职责不分离
- 每次请求创建新的 HTTP 客户端，无连接池复用
- 无缓存机制，重复查询同一城市会发起冗余 API 请求
- 超时时间、API 地址等配置硬编码在代码中
- 零测试覆盖

## 2. 目标 (Goals)
- 修复所有已知 Bug，提升服务的健壮性和防御性编程水平
- 将单文件拆分为模块化架构，实现关注点分离
- 引入内存缓存（TTL 机制），减少对外部 API 的冗余请求
- 复用 HTTP 客户端，利用连接池提升性能
- 提取配置常量，支持环境变量覆盖
- 添加单元测试，目标覆盖率 ≥ 80%
- 为后续扩展新工具（如空气质量、日出日落）奠定可插拔的架构基础

## 3. 非目标 (Non-Goals)
- 不更换底层数据源（继续使用 wttr.in API）
- 不改变 MCP 通信协议（继续使用 stdio 模式）
- 不在本次重构中添加新的天气工具（仅重构已有的 2 个工具）
- 不引入数据库或持久化存储

## 4. 范围 (Scope)
- 涉及文件：`weather-mcp-server/` 目录下的所有文件
- 重构后项目结构将从 1 个核心文件扩展到约 8-10 个文件
- 预计工作量：3-4 小时
- 重构前后功能行为应完全一致（输入输出不变）
