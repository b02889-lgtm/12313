# 提案：API 文档生成器（api-doc-generator）

## 动机

当前工作区存在以下文档相关问题：

### 现状分析

1. **文档与代码分离**：文档（如 README、各种说明文档）与实际代码分开维护，容易过时
2. **API 信息分散**：MCP 服务器、工具脚本的接口信息需要手动查看源码才能了解
3. **缺乏统一文档标准**：各模块的注释风格不一致，有的详细有的简略
4. **更新维护困难**：每次代码变更都需要手动更新对应文档，容易遗忘
5. **新人上手困难**：没有统一的 API 参考文档，理解项目需要阅读大量源码

### 具体痛点

| 场景 | 问题 | 影响 |
|------|------|------|
| 使用 file_utils.py | 需打开源码查看有哪些函数可用 | 低效，易遗漏功能 |
| 调用 MCP 服务 | 不清楚接口参数和返回格式 | 试错成本高 |
| 维护文档 | 代码改了文档忘改 | 文档失真，误导用户 |
| 新人学习 | 没有整体 API 地图 | 学习曲线陡峭 |

## 目标

建立一套**自动化 API 文档生成系统**，实现：

1. ✅ **从代码自动生成**：基于 docstring 和类型注解自动生成 API 文档
2. ✅ **统一文档标准**：采用统一的注释规范（Google/NumPy 风格）
3. ✅ **多格式输出**：支持 HTML（静态站点）、Markdown、PDF 等格式
4. ✅ **自动化更新**：代码提交时自动重新生成文档
5. ✅ **交互式浏览**：生成可搜索、可导航的文档站点
6. ✅ **版本追踪**：支持多版本文档并存

## 验收标准

| 标准 | 指标 |
|------|------|
| 覆盖范围 | 所有公开模块（scripts/、MCP 服务器）生成文档 |
| 文档格式 | 至少支持 HTML 和 Markdown 两种格式 |
| 自动化程度 | 一键生成，支持 CI 集成 |
| 文档质量 | 包含函数签名、参数说明、返回值、示例代码 |
| 可访问性 | 生成的 HTML 站点可本地浏览或部署 |
| 注释覆盖率 | 核心模块函数 docstring 覆盖率 ≥ 90% |
| 更新时效 | 代码变更后 5 分钟内文档可更新（CI 触发） |

## 范围

### 包含

- **文档生成工具链**
  - 选型并配置文档生成工具（Sphinx/pdoc/MkDocs）
  - 配置主题和样式
  - 设置输出目录结构

- **注释规范化**
  - 定义项目 docstring 规范
  - 为核心模块添加/完善 docstring
  - 添加类型注解（Type Hints）

- **自动化流程**
  - 文档构建脚本
  - CI 集成配置
  - 版本控制策略

- **文档内容**
  - API 参考文档（自动生成）
  - 使用指南（手动编写）
  - 示例代码（从 docstring 提取）

- **MCP 服务器文档**
  - 接口定义文档
  - 请求/响应示例
  - 配置说明

### 不包含

- 用户手册/教程（属于单独的用户文档项目）
- 多语言翻译
- 视频教程
- API 版本迁移工具

## 技术选型

### 文档生成工具对比

| 工具 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **Sphinx** | 功能强大，扩展丰富，支持 autodoc | 配置复杂，学习曲线陡 | 大型项目，正式文档 |
| **pdoc** | 零配置，简单快速，纯 Python | 功能有限，定制性差 | 小型项目，快速生成 |
| **MkDocs** | Markdown 原生，主题美观 | 不支持 autodoc，需插件 | 项目站点，混合文档 |
| **Pydoc** | Python 内置，无需安装 | 界面简陋，功能单一 | 临时查阅 |

### 推荐方案

采用 **MkDocs + mkdocstrings** 组合：

```
MkDocs (文档框架)
    │
    ├── mkdocstrings (自动生成 API 文档)
    │   └── griffe (Python 代码解析)
    │
    ├── material 主题 (美观的界面)
    │
    └── 插件生态
        ├── mkdocs-gen-files (动态生成页面)
        ├── mkdocs-literate-nav (简化导航)
        └── mkdocs-section-index (章节索引)
```

**选择理由**：
1. Markdown 原生，编写友好
2. Material 主题美观且功能丰富
3. mkdocstrings 支持从 docstring 自动生成
4. 配置简单，上手快
5. 支持实时预览
6. GitHub Pages 部署友好
